## v0.1.0a1 (2026-11-12)

First alpha release.

### Added

- **Three layers, installed by extras.** `tslab.lab` holds runs, stages, studies, jobs and the command line, and needs no torch. `tslab.ml` adds Lightning training, `Tensors`, `Checkpoint` and trackers (extra `ml`). `tslab.ts` adds time series interfaces, ready stages, probes and tasks (extra `ts`). The extras `chronocratic-models` and `chronocratic-datasets` add the chronocratic adapters, `analysis` adds the analysis tools, and `full` installs all of them. Python 3.12 and 3.13 are supported.
- **Runs and stages.** `tslab.lab.Run` with `RunOptions`, and `@tslab.lab.stage` to cache the result of a function under a fingerprint of its inputs and code version. A stage can run several times in one run under nested instance names, such as `evaluate[forecasting/smooth-3/h24]`. A failing instance does not stop the run: everything that depends on it is skipped, and the next run reruns only what is missing or changed. `--run.rerun` reruns chosen instances, and a dry run shows what would run. Built-in artifacts are `Json` and `Metrics`, and `external(...)` brings in results made elsewhere. Each run folder has a `status.json` and a run lock with a heartbeat, so a resubmitted job takes over its own run.
- **Configuration.** Typed dataclass configs become command-line flags through `tslab.lab.parse_config`, with named presets and `tslab.lab.REQUIRED` for values the user must give. Every run saves its `config.yaml`, and a run started from that file has the same fingerprints.
- **Training.** `Trainer` and `DataSource` interfaces, and `LightningTrainer`. It resumes safely from `last.ckpt`, stops on `max_training_time` or the SLURM time limit, and records in `training.json` why training stopped.
- **Tracking.** A CSV tracker that is always on, plus TensorBoard, MLflow and W&B trackers and a bridge to the Lightning loggers. `tslab wandb-sync` resyncs local W&B runs; it also works on a login node without torch, through the extra `wandb-sync`.
- **Time series stages and tasks.** The ready stages `tslab.ml.stages.train`, `tslab.ts.stages.encode` and `tslab.ts.stages.evaluate`, the `Encoder`, `SequenceEncoder`, `DownstreamModel` and `Probe` interfaces, and the probes `SVMProbe` and `RidgeProbe`, which follow the TS2Vec evaluation protocols. `tslab.ts.tasks.forecasting_representations` encodes a series once for all horizons, and can encode a series changed by your own stage while it still scores against the true future.
- **chronocratic adapters.** Every chronocratic model and datamodule is found automatically, and its command-line settings are generated from the parameter classes of the chronocratic libraries. Augmentations are given as recipes. `model_settings` and `data_settings` build settings by name for presets, and `ucr_datasets` and `uea_datasets` list the UCR and UEA archives.
- **Studies.** `tslab.lab.study` describes a round of experiments as grids of runs with typed settings (`Study`, `Grid`, `Override`, `setting_axis`, `from_presets`). A grid can wait for other grids with `Grid(after=(After(grid=...),))`: on SLURM this uses native job dependencies, and on a local machine the grids run in order. Machine profiles (TOML files) choose the launcher, output root, environment, SLURM resources and per-axis overrides, and can set only fields marked `MachineSetting` or `HardwareSetting`. A `tslab.toml` at the project root names the studies package and the machine of each host, so commands take short names.
- **Study commands.** `tslab study submit`, `status`, `resubmit`, `results`, `show`, `list`, `wait`, `failures`, `logs`, `cancel`, `usage`, `slurm` and `run`, plus `tslab doctor`, `tslab status` and `tslab machine`. Reporting commands support `--json`, status commands support `--exit-code` and `--watch`, and terminal output uses colored tables and names the next command to run. Optional code snapshots (`--code-snapshot`) keep queued and resubmitted jobs on the code they were submitted with.
- **SLURM.** Grids are submitted as job arrays named after a `job_name` template. Jobs run through `srun` with one task per GPU, and training uses all tasks for distributed training. A `SIGUSR2` before the time limit saves a checkpoint and marks the run as interrupted. Interrupted runs can be resubmitted automatically, or requeued in place inside a chain (`chained_retry = "requeue"`). Preemption and node failure do not count against the retries of a run. `tslab study status` shows why a queued job waits, and `tslab doctor` checks a profile against the limits of the cluster.
- **Local launches.** Local launches run several runs at once. They find GPUs automatically, lock them across studies, skip GPUs that are busy, or use CPU slots when there is no GPU. A launch keeps the machine awake, can run detached (`--detach`), honors a time limit per run, and stops cleanly on `Ctrl-C`, `SIGTERM` and `SIGHUP`. If the launcher dies, its runs stop too.
- **Analysis.** `tslab.lab.analysis` (extra `analysis`) has paired tests (Wilcoxon, Holm, Friedman), critical-difference diagrams, a LaTeX numbers file, notebook display blocks and a results frame with coverage and baseline helpers.
- **Project templates.** `tslab new` creates a `lab` or `ts` project with scripts, presets, an example stage and augmentation, synthetic toy data, studies (one of them chained), an analysis notebook, a smoke test, an `AGENTS.md` and an agent skill that guide coding agents through the project. Inside an existing Python project, `tslab new` links the new project in as a uv workspace member; `--layout {standalone,workspace}` overrides the automatic choice. The example SLURM machine profile is named `hpc` (`machines/hpc.toml`, `--machine hpc`).
- **Documentation and examples.** A user guide and API reference on Read the Docs. `examples/minimal` uses only the lab layer. `examples/advanced` trains TS2Vec with a user transform stage that has a failing instance, frozen covariate channels and nested instance names.
